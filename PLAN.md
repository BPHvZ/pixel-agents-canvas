# Pixel Agents Office: Product plan

**Status:** Phase 0 and UI design approved; implementation in progress, not release-ready. Verified delivery and remaining gates are tracked in [docs/implementation-progress.md](./docs/implementation-progress.md#status-snapshot--2026-10-18).
**Last updated:** 2026-10-18

## Product goal

Deliver a genuinely useful, installable, read-only session dashboard in a pixel-art office—not a demo presented as a product. Target one canvas experience in both VS Code and the GitHub Copilot App, with the Copilot App as the finalized installation host; VS Code Canvas support remains a preview and may change. Use the repository folder `.github/extensions/pixel-agents-canvas` on `main` as the canonical App import URL; a compatible Gist URL is optional, with no project-maintained mirror. New imports use the latest merged code, which may precede a tagged source release; release-readiness gates apply to publishing source releases only. This is an initial-install procedure, and update behavior is unspecified. A paid GitHub Copilot plan must not be required for meaningful use. The hosts may still require GitHub sign-in and may accept third-party model providers, BYOK, or proxy-backed model routes. Keep host, harness/activity source, model route, and billing as separate facts; show only what the relevant host exposes reliably, and never infer the activity provider from the selected model. Show all Copilot/Codex coding-agent sessions only where supported host/provider APIs make them observable; disclose coverage differences rather than inventing activity. Any synthetic activity preview is solely an explicitly labeled onboarding/test aid.

## Product definition

### V1 dashboard

The office is the primary view and must remain useful without sample data. For each observable session and provider-identified agent, show identity when available, the activity source/harness and discovery source, provider-reported lifecycle/waiting state, safe task summary when available, and last activity/freshness. Offer open/focus only where a public host route is supported and tested. Keep model and billing routes out of the default office; optional details may show them only when the host reports them reliably. Make missing fields explicit instead of fabricating values. Distinguish unsupported activity source, supported-but-unavailable integration, connected with confirmed no sessions, stale/disconnected source, and discovered sessions.

Represent each distinct provider-established agent identity—including separately identified subagents—as a character, grouped into a session cluster only when the relationship is provider-reported. Do not infer extra workers or hierarchy from tool events/text. The shared office floor and clusters do not imply shared files or workspace. Stable character appearance, local nickname, and fictional voice flavor are decorative, not provider roles or task knowledge. Office-wide fictional vignettes may cross clusters without asserting collaboration; they never alter factual lifecycle, sorting, or actions. See [ADR 0008](./docs/adr/0008-stateful-office-ambience.md) for the factual/fictional boundary and office-world lifecycle.

Show active sessions first and keep explicitly ended characters visible by default; the Show ended control may hide them. Never infer completion from an idle timeout, archive, stale observation, or runtime unload. Keep a compact source-health indicator in the office and a recent global feed of generic provider transitions; expose detailed coverage in an optional, hidden-by-default secondary view.

The office uses state-specific theatrical animation with readable factual status labels. Working agents use varied desk-centered poses/props; when a fresh event changes their state, fiction yields immediately to the new factual cue. Fresh explicitly idle agents may join authored group vignettes; Unknown/Stale/disconnected agents get solo fiction only; ended agents may socialize with idle or ended characters but never appear Working. A fictional quiet-cluster treatment (dim room, hidden title/motifs, transient spooky ambience) may run when no fresh agent is Working, Waiting, or Failed, even with no provider idle event or a disconnected source; it does not change provider state or assert that a session ended. Only explicit provider session closure yields the factual Session ended marker. Vignettes and dialogue have separate toggles and never enter the factual feed. Office props/world state persist for the canvas instance and are visibly tidied. See [ADR 0008](./docs/adr/0008-stateful-office-ambience.md) for scene cadence, accessible bubbles, quiet/abandoned distinction, motifs, personalization, and cleanup.

### Interaction and boundary

Read-only means the extension never launches a model turn, sends/steers a prompt, assigns work, stops/pauses an agent, or orchestrates. Users may open/focus an underlying conversation only when a documented host/provider navigation route is supported and tested; otherwise disclose navigation as unavailable rather than guessing. One user/current host context only in V1; no shared-office synchronization. Do not impose an arbitrary product cap; establish practical performance limits by testing.

### Data and consent

Provider metadata is the default source for sanitized task summaries, but a provider title/name is not inherently sanitized and may contain sensitive user text. Show a bounded provider title in the roster by default with global and per-session hide controls; identify it as a provider title, not as a verified-safe summary. Title-derived scene motifs are deterministic local decoration; hiding the title text does not hide the motif, and the control must disclose this. For Codex thread listing, never surface `preview`, transcript turns, prompt text, tool input/output, file paths, or credentials. Activity callbacks must ignore content-bearing arguments and retain only generic statuses unless a specific field is explicitly approved. The dashboard adapter does not intentionally expose or retain prompt/tool content; this source-level statement is not a guarantee about host/runtime/provider/proxy egress or logging. Prompt summarization remains off and unavailable until its on-device/transient/log-free properties are demonstrated across both host and selected model route. Keep factual activity in memory only; clear it when the extension/host closes. Office props are separate fictional presentation state, cleared when the canvas closes.

Enable activity sources independently. A Copilot CLI harness routed through an OpenAI/Codex model remains a Copilot CLI activity source; its model vendor and billing route are not the source identity. Separately, Codex CLI/app-server can discover Codex-owned threads after explicit user enablement and only through supported metadata-first interfaces. This uses the user's installed/authenticated Codex CLI; do not infer CLI access or billing eligibility from a ChatGPT subscription alone. Copilot SDK hooks may be limited to the hosting Copilot conversation. Do not require equal coverage; show source limitations.

## Current implementation and gap

The committed initial implementation (`35e7fe7`) listens to hosting Copilot session hooks and renders its observed session plus metadata-only Codex threads. After explicit opt-in, the Codex adapter paginates `thread/list` with `useStateDbOnly`, discards unapproved content fields, resumes active threads with `excludeTurns: true`, and tracks notifications. It no longer creates threads. Runtime-compatible JavaScript and custom declarations pass ESLint and strict TypeScript; the 35-test suite includes negative no-`any` checks. The browser module is checked separately from HTML. Portable agent guides and skills were published in `d7bf978`, with the ADR/progress maintenance gate in `f8bab81`; CI passed for all three commits.

The implementation in `43c2ab8` (pushed to `develop`, CI passed) adds unified provider health/capabilities, opt-in discovery recovery, provider-reported Codex session-tree grouping and Copilot subagent identities, factual event feed/coverage, checked clustered UI, local appearance/title controls, and the separate stateful fictional-office layer (ADRs 0001–0008). The current VS Code hosting session has opened and reopened the new canvas with the same instance URL and successfully invoked its read-only action. A disposable real CLI/SDK session additionally verified discovery, open/action/reopen/close, listener shutdown, and clean runtime exit without a model turn. Fixture-browser checks cover keyboard selection, preference persistence, title hiding with motifs retained, provider toggles, reduced motion, and a narrow viewport. The 120-test suite, 12 browser regressions, and the previous renderer scale check passed for that commit. A user-approved ADR 0008 refinement is now in progress: animated one-line speech bubbles, varied non-repeating per-character/state dialogue, lively solo fiction for unknown/stale/offline characters, off-duty behavior for explicitly ended agents, and a fictional quiet-cluster mode kept distinct from provider-confirmed abandonment. A targeted adapter regression keeps Copilot's stable internal `agentName` and discards `agentDisplayName`: the upstream SDK schema notes this field may be the task description for task-tool subagents ([pinned schema](https://github.com/github/copilot-sdk/blob/b96cd2b54f7eb87458fd50f485a751c712e88f62/nodejs/src/generated/session-events.ts)). The schema exposes subagent start/completion/failure, but no per-agent idle heartbeat; after 45 seconds without an explicit observation, the agent becomes Unknown/Stale rather than being kept falsely Working or marked idle. Targeted Chrome regressions cover speech styling, reading window, reduced motion, quiet title/motif suppression, concise freshness/count labels, and preservation of provider status/feed; full world integration remains pending. This refinement does not change factual provider state/feed semantics. Latest Copilot App visual verification remains outstanding. Unrelated Copilot conversation enumeration and cross-session navigation remain unsupported. No release-completion claim is made from local tests or earlier Phase 0 evidence; preview/sample activity is never a product fallback.

## Proposed architecture

1. **Canvas shell and host packaging** — Keep the canvas as the product surface. Validate supported extension packaging, process/runtime permissions, and lifecycle in both target hosts. A single artifact is the goal; allow host-specific packaging that shares product/core code if required rather than weakening access or requiring a Copilot subscription.
2. **Provider-neutral domain model** — Normalize activity-source-owned sessions, agent identities, reported parent/session relationships, lifecycle, provider titles, timestamps, freshness, discovery source, and capabilities. Preserve provenance and represent absence/unknown explicitly; use custom JSDoc/TypeScript declaration types at the runtime-compatible JavaScript interfaces; keep host, harness/activity source, model route, and billing route separate.
3. **Independent adapters** — Copilot CLI hooks consume the hosting Copilot CLI session only; selecting a Codex/OpenAI model through a proxy does not turn it into a Codex CLI activity source. A separate Codex adapter uses the explicitly enabled local stdio app-server to discover Codex CLI-owned threads. Adapters distinguish unsupported, unavailable, confirmed empty, stale/disconnected, and active discovery.
4. **Office and coverage views** — Main view maps provider-established agents into session clusters and prioritizes active work. An optional hidden-by-default view explains provider scope, availability, discovered session count, freshness, and known limitations. Both views expose accessible textual status; animation is supplementary.
5. **Privacy boundary** — Field-select provider metadata; never copy full payloads. Discard Codex `preview`/turns and ignore content-bearing Copilot hooks. Provider titles are labeled as such, bounded, hideable, and may be sensitive; hiding title text does not hide derived motifs. Keep provider activity and fictional scene state transient; persist only user-selected appearance/display preferences. Prompt summarization is out of scope for V1 pending an end-to-end audit and separate approval.

## Delivery phases and acceptance criteria

Every feature and work item must be supported by an accepted ADR before implementation. Reuse existing decisions when they cover the work; create or update an ADR and obtain approval when coverage is missing or a decision changes. During development, update this plan and [implementation progress](./docs/implementation-progress.md) after each slice: keep current implementation/gaps and next steps accurate, and record the covering ADR, verified results, remaining work, and blockers in the tracker.

### Phase 0 — Feasibility / release gates
- Verify current official app-server `thread/list`, metadata fields, lifecycle notifications, parent/subagent representation, archive/terminal semantics, pagination, and supported CLI versions. Demonstrate discovery of existing threads without reading transcript content in metadata-only mode.
- Verify explicit process consent, local stdio launch/stop, host lifecycle, and source-level data minimization in both canvas runtimes. Do not claim host-wide zero-egress or absence of provider/runtime logging without an end-to-end audit.
- Verify official host navigation/open-focus capability, or document its absence.
- Verify canvas extension installation/packaging and useful operation without an active paid GitHub Copilot plan, using the documented third-party-model/BYOK or proxy routes as appropriate. Test whether one artifact works in both hosts; decide packaging accordingly. GitHub sign-in may still be required by the host.
- Prompt summarization is deferred for V1 because the local/transient/log-free boundary is not established. Revisit only after an end-to-end host/runtime/model-route audit and a separate user decision.
- **Gate:** if a required capability is unsupported, narrow and clearly label that source's coverage; never substitute fictional office activity for missing provider activity. Revisit product viability only if no provider path can meet the minimum usefulness bar.

### Phase 1 — Domain and provider-neutral core
- Implement/test session-versus-agent identity, provider-established hierarchy, provenance, partial/unknown values, terminal states, stale/fresh status, and independent provider availability.
- Test malformed, duplicate, out-of-order, and missing provider signals without implying false work or completion.
- Enforce custom domain/protocol types in checked runtime-compatible JavaScript and TypeScript declarations. `npm run check` must pass ESLint (including no explicit/unsafe `any`), strict TypeScript with implicit `any` disallowed, and regression tests. Type-check browser code separately from HTML and do not install the host-injected SDK into the extension.

### Phase 2 — Codex existing-session discovery
- After Phase 0 validation, implement explicit opt-in local app-server lifecycle and list/subscribe metadata for supported existing threads.
- Do not access prompts, transcripts, or tool payloads for V1 task summaries or office personalization; prompt summarization is deferred pending an end-to-end audit and a separate product decision.
- Test pagination, process failure/restart, archive/completion, thread ownership boundaries, relationships, and cleanup with fixtures plus a live CLI where available.

### Phase 3 — Copilot and navigation adapters
- Implement the documented hosting-conversation hooks and expose their narrow scope.
- Add open/focus only when confirmed by a supported host/provider API; do not call guessed internal commands.
- Ensure providers work independently and a missing Copilot entitlement does not block Codex functionality.

### Phase 4 — Product UI and consent
- Build clustered agent representation, active-first ordering, visible-by-default explicitly ended/off-duty identities with a hide-ended control, optional coverage panel, provider-title visibility controls, freshness, and explicit per-source states.
- Implement the approved factual/fictional office presentation and personalization in [ADR 0008](./docs/adr/0008-stateful-office-ambience.md); do not implement prompt-summary consent in V1.
- Meet keyboard, screen-reader, reduced-motion, responsive, and readable status acceptance criteria.

### Phase 5 — Distribution and release verification
- Verify GitHub Copilot App installation from the canonical project-folder URL on `main` and a compatible Gist URL, plus provider combinations (Copilot only, Codex only, both, neither), no Copilot entitlement, no-session/unsupported/offline states, open/focus, and practical scale. Keep VS Code installation and lifecycle checks as preview acceptance, not as finalized distribution support.
- Document installation, consent, data boundaries, provider-specific coverage, limitations, and troubleshooting. App URL instructions cover initial imports only; update behavior is unspecified. Publish tagged source releases only with product behavior aligned with labels; preview remains off by default and visibly separate.

## Decisions already made

See ADRs 0001–0008. In brief: read-only local-first factual dashboard with a separately labeled fictional office layer; one product targeting both hosts with truthful host-specific scope; no Copilot subscription gate; independent providers; explicit Codex process consent; supported API discovery only; transient provider activity; metadata summaries by default; prompt summarization out of scope for V1; provider-established agent identities/relationships; active sessions by default; optional coverage and inactive-session views. Fiction is never a substitute for missing provider activity.

## Unresolved validation questions

These are ongoing validation and release-verification items, not silently assumed product decisions:

- Does Codex app-server `thread/list` expose enough safe metadata for useful summaries/status without transcript reads, and can it report subagent identities/links across supported CLI versions?
- Can the same installable artifact work in both hosts, or is shared-core host-specific packaging required?
- Can prompt text be summarized on-device transiently in both hosts without host-side external processing, content logs, or retained raw text? Until proven, this remains out of scope.
- Continue accessibility and representative live-data checks beyond the synthetic 100-session/300-agent renderer smoke test.

## Inspiration and evidence

The public READMEs are inspiration, not product requirements. `agent-virtual-office` describes real session/CI status integrations and playful reactions, emphasizing actual status and no invented dialogue. `agent-office` advertises chat, task assignment, saved results, integrations, and decisions while warning that it is early development; those control features are outside this product's read-only scope. `pixel-agents` describes one character per agent terminal and separate characters for observable subagents/teammates, a provider-neutral hook-provider interface, and persistent editable layouts; its README lists Codex as roadmap rather than shipped support. These examples support exploring grouped characters and adapter boundaries, but do not prove this host can observe equivalent signals.
