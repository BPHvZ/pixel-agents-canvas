# Phase 0: Host consent and crash-cleanup lifecycle

**Checked:** 2026-10-17. **Scope:** official VS Code and GitHub Copilot App/CLI documentation and upstream source only; no current-repository implementation inspection or new runtime test. **Documented** means a stated product/API contract. **Source-observed** means behavior in the linked upstream implementation, not a compatibility promise. **Unknown** means these sources do not establish the behavior.

## Consent and trust gates before project extensions execute

| Host / question | Finding | Evidence and limitation |
|---|---|---|
| VS Code workspace trust | **Documented:** new folders open in Restricted Mode by default; workspace trust lets users decide whether code in a project can be executed by VS Code and extensions. Extensions that have not opted into trust support are disabled or limited in Restricted Mode. Trust is a workspace-level gate, not a per-extension approval prompt on every activation. | [Workspace Trust](https://code.visualstudio.com/docs/editing/workspaces/workspace-trust), **Restricted Mode**, **Extensions**, and **Trusting a workspace**. The startup prompt defaults to `never`; new folders show a trust banner. This is VS Code extension-host policy, not proof that Copilot App canvas extensions are governed identically. |
| Copilot CLI project extensions | **Documented:** project extensions load only from trusted folders or with explicit opt-in. In prompt-mode automation, `GITHUB_COPILOT_PROMPT_MODE_EXTENSIONS=true` enables loading for that invocation; docs warn to enable it only for trusted repository code and state this does not grant tool permissions. | [CLI command reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference), environment variables; [CLI programmatic reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-programmatic-reference), **Running dynamic workflows**. The prompt-mode variable is not documented as the Copilot App’s project-extension consent mechanism. |
| GitHub Copilot App canvas extensions | **Documented:** canvas extensions can be project-scoped under `.github/extensions`, commonly with `package.json` and an entry file such as `extension.mjs`; plugins are installed through the app’s Customize UI. **Unknown:** the App canvas-extension docs do not specify whether discovery/execution of a project-local extension requires a trust confirmation, per-extension approval, or another gate. | [Working with canvas extensions](https://docs.github.com/en/copilot/how-tos/github-copilot-app/working-with-canvas-extensions), **Discovering canvases**, **Creating a canvas**, and **How canvas extensions are structured**; [Customizing the Copilot app](https://docs.github.com/en/copilot/how-tos/github-copilot-app/customize-github-copilot-app). App sessions are built on Copilot CLI ([agent sessions](https://docs.github.com/en/copilot/how-tos/github-copilot-app/agent-sessions)), but that fact alone does not document that the CLI’s exact project-extension gate applies to App canvas loading. Do not report an App consent dialog as guaranteed on this evidence. |
| Is extension activation itself a consent gate? | **Documented:** in VS Code, `activate` runs when its declared activation event occurs; activation events control when an extension starts, not whether the user has trusted its code. | [Extension Anatomy](https://code.visualstudio.com/api/get-started/extension-anatomy) and [Activation Events](https://code.visualstudio.com/api/references/activation-events). Workspace Trust is the separate trust mechanism cited above. |

**Decision implication:** VS Code has a documented workspace trust gate; Copilot CLI documents trusted-folder / explicit-opt-in behavior. For Copilot App project canvas extensions, the reviewed first-party docs establish project discovery and structure but not a pre-execution consent guarantee. Treat App consent behavior as **unverified**, and avoid claiming the user approves each extension before it runs unless confirmed against the target App/runtime.

## Cleanup: normal shutdown versus abrupt failure

| Host / lifecycle | Documented or source-observed behavior | Limit |
|---|---|---|
| VS Code extension deactivation | **Documented:** an extension’s optional `deactivate` function is an opportunity to clean up when VS Code shuts down or the extension is disabled/uninstalled. **Source-observed:** current VS Code source calls deactivation for activated extensions on its extension-host termination path and allows async deactivation up to 5 seconds before exiting. | [Extension Anatomy](https://code.visualstudio.com/api/get-started/extension-anatomy); [VS Code `extHostExtensionService.ts`](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/api/common/extHostExtensionService.ts#L230-L278). Deactivation is an opportunity, not a guarantee that every cleanup action succeeds or finishes. |
| VS Code host process shutdown | **Source-observed:** current desktop source waits for extension hosts during window shutdown (up to 6 seconds); it also forcefully kills a host process found still alive after its exit notification. | [VS Code `extensionHostStarter.ts`](https://github.com/microsoft/vscode/blob/main/src/vs/platform/extensions/electron-main/extensionHostStarter.ts#L30-L40) and [process-exit handling](https://github.com/microsoft/vscode/blob/main/src/vs/platform/extensions/electron-main/extensionHostStarter.ts#L75-L105). These implementation details are not a public cleanup contract for extension-owned child processes. |
| Copilot App canvas close | **Source-observed/API declaration:** the Copilot SDK’s optional `onClose` callback is notified when a canvas instance is closed by the user, agent, or host; it is fire-and-forget, its return value is ignored, and callback errors are logged rather than surfaced. | [Copilot SDK `canvas.ts`](https://github.com/github/copilot-sdk/blob/main/nodejs/src/canvas.ts#L100-L150). Canvas close is not the same as session shutdown or process-crash notification; the declaration does not promise `onClose` during a crash. |
| Copilot SDK graceful client stop | **Source-observed:** an explicit `CopilotClient.stop()` disconnects active sessions, requests runtime shutdown, closes the RPC connection, signals EOF to an SDK-owned stdio process, waits for exit, and attempts normal termination if it remains alive. `forceStop()` force-closes the connection and sends `SIGKILL` to an SDK-owned CLI process. | [Copilot SDK `client.ts`](https://github.com/github/copilot-sdk/blob/main/nodejs/src/client.ts#L1100-L1360) and [`forceStop()`](https://github.com/github/copilot-sdk/blob/main/nodejs/src/client.ts#L1380-L1455). These are explicit SDK operations; they do not establish that the Copilot App always invokes them on every exit path or that they clean up processes an extension spawned independently. |
| Abrupt host/process crash | **No host callback guarantee; isolated child cleanup observed:** reviewed docs/API/source do not establish that an abrupt host kill invokes extension cleanup, canvas `onClose`, or SDK `stop()`. A local probe launched Codex CLI 0.163.0 `app-server --listen stdio://` with piped stdio, initialized it, then SIGKILLed the owning Node process. The Codex child exited after its stdin pipe closed (within the 5-second observation window); no orphan remained. Separately, the Copilot App bootstrap's parent watchdog was exercised with a synthetic extension child, which it terminated after parent exit. | These checks demonstrate cleanup paths for the tested process topology, not a contractual guarantee for every host failure mode or every process the host may spawn. They did not hard-kill VS Code or Copilot App itself. |

**Decision:** Phase 0 accepts the documented VS Code workspace-trust mechanism and the user's deliberate use of the project canvas in Copilot App as consent to project-extension execution. Since the Copilot App's canvas docs do not establish a separate loader approval prompt, the product will not promise one; the user may review this code before opening the canvas. Starting the Codex process remains separately opt-in in the UI. The product requires graceful cleanup on normal lifecycle events and handles lost stdio/parent exit for its provider child; it does not claim callbacks or cleanup are guaranteed after arbitrary host crashes. The observed Codex pipe-close behavior plus the App bootstrap watchdog and normal-shutdown tests are sufficient for Phase 0; validate changed process topology during release testing.
