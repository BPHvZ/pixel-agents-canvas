# Phase 0 privacy evidence report

**Reviewed:** 2026-10-17. **Scope:** source/documentation review only; no runtime packet capture, host telemetry audit, or credential/config inspection. Statuses describe the cited evidence, not a guarantee of what a particular deployment sends.

## Data-flow claims

| Claim | Status | Evidence and limitation |
|---|---|---|
| Copilot hook callbacks can receive prompt and tool content. | **Documented** | The [Copilot SDK `user-prompt-submitted` hook](https://github.com/github/copilot-sdk/blob/main/docs/hooks/user-prompt-submitted.md), **Input** table, defines `prompt` as the submitted user prompt. The [SDK `pre-tool-use` hook](https://github.com/github/copilot-sdk/blob/main/docs/hooks/pre-tool-use.md), **Input** table, defines `toolName` and `toolArgs`; the [SDK `post-tool-use` hook](https://github.com/github/copilot-sdk/blob/main/docs/hooks/post-tool-use.md), **Input** table, defines `toolArgs` and `toolResult`. The [Copilot hooks reference](https://docs.github.com/en/copilot/reference/hooks-reference), **Hook event input payloads**, `userPromptSubmitted`, `preToolUse`, and `postToolUse`, documents analogous CLI hook payloads, including prompt, tool input, and successful tool result. Hook data is therefore content-bearing by contract; actual forwarding depends on callback behavior. |
| The inspected extension's Copilot hook callbacks read or forward hook arguments. | **Documented: no, for these callbacks** | Repository [extension.mjs](../.github/extensions/pixel-agents-canvas/extension.mjs#L25-L35), `copilotHooks` / `update`, defines each hook as `() =>` with no input parameter and calls `record` only with fixed event/state plus a timestamp. This is a code-level observation for the reviewed source, not a claim about other SDK/host processing. The SDK input contract above confirms the unused parameter could carry prompt/tool data. |
| Copilot/VS Code hosts transmit no prompt, tools, or other data online. | **Not established** | GitHub's [Copilot CLI overview](https://docs.github.com/en/copilot/concepts/copilot-surfaces/copilot-cli), **Using your own model provider**, documents an optional configured provider endpoint; it does not define complete host egress or all other service traffic. VS Code [Telemetry](https://code.visualstudio.com/docs/configure/telemetry), **Managing online services** and **Extensions and telemetry**, explicitly says VS Code uses online services beyond telemetry and extensions may separately use online services. These sources do not prove zero egress for the host, CLI, extensions, provider, or a specific session. |
| CLI/SDK hook configuration can send hook input outside the process. | **Documented** | The [GitHub Copilot hooks reference](https://docs.github.com/en/copilot/reference/hooks-reference), **HTTP hooks**, specifies that an HTTP hook sends the input payload as a JSON `POST` to its configured URL; HTTPS is required by default with documented localhost exceptions. The same reference documents command hooks and hook payloads. This establishes a configurable data path, not that the inspected extension configures HTTP hooks. |

## Telemetry, logs, and host boundaries

| Claim | Status | Evidence and limitation |
|---|---|---|
| VS Code core telemetry has a default and disable control. | **Documented** | [VS Code Telemetry](https://code.visualstudio.com/docs/configure/telemetry), **Disable telemetry reporting**, lists levels `all`, `error`, `crash`, and `off`; `off` silences VS Code telemetry going forward, with possible collection before the setting changes. The page does not say this disables extension telemetry or non-telemetry online services. |
| VS Code `telemetry.telemetryLevel=off` disables telemetry from every extension. | **Documented: false** | Same VS Code page, **Extensions and telemetry**, says extensions may collect their own usage data and it is not controlled by `telemetry.telemetryLevel`. The [extension-author telemetry guide](https://code.visualstudio.com/api/extension-guides/telemetry), **Without the telemetry module** and **Custom telemetry setting**, directs extension authors to respect `isTelemetryEnabled` / `onDidChangeTelemetryEnabled`; that is author guidance, not evidence every extension complies. |
| Extension output/log channels may persist locally; that is distinct from automatic upload. | **Documented** | VS Code [API reference](https://code.visualstudio.com/api/references/vscode-api#OutputChannel), `OutputChannel` / `LogOutputChannel`, exposes extension-created output and log channels. VS Code first-party implementation [`extHostOutput.ts`](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/api/common/extHostOutput.ts), `ExtHostOutputService.createOutputChannel`, assigns a `.log` path under the extension log directory for `{ log: true }`, while ordinary channels use a separate path; see also its `ExtHostOutputChannel.append`/`log` methods. Whether content is recorded depends on extension choice, host version, and log levels. VS Code [Telemetry](https://code.visualstudio.com/docs/configure/telemetry), **Output channel for telemetry events**, further documents local `telemetry.log` when event tracing is explicitly enabled. Local logging itself does not establish transmission. |
| Child-process stdout/stderr is always persisted by VS Code, or always discarded. | **Not established** | [Extension Host](https://code.visualstudio.com/api/advanced-topics/extension-host) documents local/remote Node.js and browser extension hosts and their location/runtime, but does not define a blanket persistence or forwarding rule for arbitrary child-process stdout/stderr. A specific extension/host path must be inspected or observed. |
| Copilot CLI telemetry defaults and a CLI-wide disable switch are fully documented by the sources reviewed here. | **Not established** | The public [Copilot CLI overview](https://docs.github.com/en/copilot/concepts/copilot-surfaces/copilot-cli) describes CLI features, custom provider configuration, and permissions but does not establish the complete telemetry default, payloads, endpoint set, or a telemetry-off control. Do not equate VS Code telemetry controls with Copilot CLI/SDK telemetry. The [Copilot CLI changelog](https://github.com/github/copilot-cli/blob/main/changelog.md) documents OpenTelemetry instrumentation, but not a complete default/disable guarantee. |

## Model backends, endpoints, and transmission

| Claim | Status | Evidence and limitation |
|---|---|---|
| BYOK and an OpenAI-compatible custom endpoint are the same as the host's default backend. | **Documented: false** | GitHub's [Copilot CLI overview](https://docs.github.com/en/copilot/concepts/copilot-surfaces/copilot-cli), **Using your own model provider**, presents custom endpoint selection separately from GitHub-hosted models. It names `COPILOT_PROVIDER_BASE_URL`, `COPILOT_PROVIDER_TYPE`, `COPILOT_PROVIDER_API_KEY`, and `COPILOT_MODEL`, including OpenAI-compatible endpoints and local Ollama/vLLM examples. This describes an explicit user-chosen provider option; it does not attribute that route to a default host or prove all traffic follows it. |
| OpenAI API requests necessarily go online to OpenAI's service. | **Partially documented** | OpenAI [API Overview](https://developers.openai.com/api/reference/overview), **Start here** and **Authentication**, documents HTTP API calls authenticated by API key or short-lived token. It describes API service behavior, not a client's selected network path when configured for a proxy/compatible local backend. |
| OpenAI API content is not used for training and has no retention. | **Documented: only in part** | OpenAI [Data controls](https://developers.openai.com/api/docs/guides/your-data), opening statement says API data is not used to train/improve models unless opted in. **Data retention controls for abuse monitoring** says default abuse logs may contain prompts/responses and are retained up to 30 days (with stated exceptions). **Zero Data Retention** and **Modified Abuse Monitoring** require approval and have endpoint/application-state limitations. No universal no-retention claim is supported. |
| VibeProxy routes traffic only locally and therefore prevents online disclosure. | **Partially documented / not established as a privacy guarantee** | The [VibeProxy project README](https://github.com/automazeio/vibeproxy/blob/main/README.md), **Codex Configuration**, says its OpenAI-compatible endpoint can be selected in Codex config (example `http://127.0.0.1:8317/v1`) and that this routes Codex agent traffic through VibeProxy; **Server Management** and **Advanced Configuration** describe its server and config. This establishes a user-configured local proxy hop, not the proxy's complete downstream destinations, content handling, logging, or zero-egress behavior. The README also documents OAuth/API-key provider integrations, so local listener does not mean the model service is local. |
| VS Code telemetry off disables provider/model traffic or extension online services. | **Documented: false** | VS Code [Telemetry](https://code.visualstudio.com/docs/configure/telemetry), **Extensions and telemetry** and **Managing online services**, separates core telemetry, extension telemetry, and online services; disabling telemetry is not offline mode. A provider request remains a separate data flow governed by the selected backend and its policies. |

## Repository-source findings

| Claim | Status | Evidence and limitation |
|---|---|---|
| Copilot hook callback ignores supplied input; displayed labels are generic and stored in memory. | **Documented** | [extension.mjs](../.github/extensions/pixel-agents-canvas/extension.mjs#L21-L35), `record` and `copilotHooks`, sets generic event labels and uses zero-argument closures. [state.js](../.github/extensions/pixel-agents-canvas/src/state.js#L4-L50), `createStore`, stores agent rows in a closure-owned `Map`; `clear()` removes them. This supports in-process memory-only retention for this store, not zero-egress for the whole host or CLI. |
| Codex integration selects metadata from thread listings and maps approved notification fields, ignoring other payload fields. | **Verified in the adapter source; not a host-wide logging guarantee** | [codex-client.js](../.github/extensions/pixel-agents-canvas/src/codex-client.js), `listThreads` uses `useStateDbOnly: true`, paginates active/archived results, and projects only ID/title/parent/status/timestamps/source/modelProvider plus archive and monitoring state. It drops `preview`, turns, paths, and other response fields before returning them. Active threads resume with `excludeTurns: true`; notifications are accepted only for explicitly tracked thread IDs and reduced to generic state/turn/lifecycle updates. The product no longer calls `thread/start` or sends `cwd`. The process necessarily receives JSON-RPC lines and list results in memory; this source review does not establish host/runtime logging or egress behavior. |
| This repository extension writes prompt/tool content to its own file or telemetry channel. | **Not established by reviewed extension source** | Searched `.github/extensions/pixel-agents-canvas` for console logging, output channels, filesystem log writes, and request endpoints. No such code was found in the reviewed files; this bounded source review does not establish host/CLI logging behavior or absence of transmission elsewhere. The extension uses a loopback HTTP server for its canvas, with `/state` and the opt-in `/codex/enable` route (local UI transport, not evidence of external egress). |

## Safe statement

The inspected extension callback bodies ignore their supplied Copilot hook payloads and record only generic labels in a process-local in-memory store. The current Codex adapter field-selects thread-list metadata, resumes active threads with turns excluded, and reduces tracked notifications to compact status/turn/lifecycle signals; it neither reads nor displays previews, turns, tool payloads, or file paths. The renderer uses loopback HTTP; the product no longer creates empty threads. These source-level observations show that the dashboard adapter does not intentionally inspect prompt/transcript/tool content. Provider titles/names may still contain user text and are not guaranteed sanitized. The installed Copilot SDK hook API calls the callbacks during model turns; it does not establish whether the host/model runtime independently logs or transmits the supplied hook inputs. They do **not** establish zero egress or prove that the Copilot CLI, host, VS Code, Codex process, selected model provider, or configured proxy never sends or logs content. VS Code telemetry off only controls VS Code telemetry; extension telemetry and provider traffic are distinct. A custom endpoint/VibeProxy route is a different backend, not a host-wide privacy guarantee.
